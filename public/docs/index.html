$How BitLLM works

One binary, four jobs: client, gateway, server and relay. This page describes every moving part: how a fresh install meets the network, how a request finds a GPU, what is signed, what is only claimed, and what happens when something dies.

BitLLM is a peer-to-peer inference network for open models. There is no coordinator in the request path, no central queue, and no database of who served what. A node joins by finding one seed, then learns the rest from a Kademlia DHT and a gossip topic. The model names are ordinary strings; the network only routes on them. The binary is the same for everybody, and flags decide which hats it wears.

Short version. Resolve one seed. Ask the DHT who serves a model. Open an encrypted stream, direct if the routers allow it and otherwise through a relay. Stream the tokens. Sign a receipt for the work. Everything else on this page is detail.

Overview

Four loops run inside a serving node. A node that only uses the network runs the gateway and listens to gossip:

  • Gossip. Every 10 seconds a serving node publishes an announce: version, the models it serves, free slots, queue depth, whether it can relay, and optionally a coarse location and weight hashes. Peers keep the latest announce for three periods, so a node that stops answering disappears from routing within about 35 seconds.
  • DHT providers. Every two minutes a serving node records itself as a provider of each model it serves, under a key derived from the model name. Provider records expire after 24 hours; the refresh repairs a record lost while the DHT had no peers.
  • Upstream check. A serving node asks its local model server for /models before it announces. A stopped vLLM makes the node go quiet instead of advertising capacity it cannot use.
  • Gateway. The local HTTP server on 127.0.0.1:7778 accepts OpenAI and Anthropic requests, chooses a peer, and streams the answer back. It is the only part a user normally touches.

Only three things are centrally hosted, and none of them carries inference traffic: the DNS seed list, the static site and installers, and GitHub releases. DNS is read once at startup (and on redial); after that, peers find each other.

Roles and reachability

Roles are not separate programs. They are combinations of flags and network position.

clientbitllmoutbound internetlocal gateway only; no model, no inbound port
serving node--upstream URLa local OpenAI-compatible serverannounces models, accepts inference streams, signs receipts
public relay--public --upstream URLinbound TCP and UDP 4001, and a model to serveDHT server, relay for NATed peers; still joins the seeds
seed--dht-servera public relay listed in DNSfirst contact; starts alone, answers DHT queries, relays

A serving node can be behind NAT or CGNAT. It does not need a public address or a port forward: it reserves a relay slot and, when the routers cooperate, upgrades to a direct connection. A public relay is any host that can accept inbound TCP and UDP on 4001; it needs no DNS record, but today it must serve a model: a node announces only with --upstream, and peers reject an announce with no models. A seed is a public relay that is also named in _dnsaddr.bootstrap.bitllm.org, so a fresh install can find it without knowing anyone.

This split is deliberate. One seed is enough to join, but it must not be the only relay: relay capacity should grow with the number of public nodes, not with DNS edits. Every public node that serves a model announces relay=true; NATed nodes add those peers to their autorelay candidate set alongside the seeds.

First contact

A node with no --bootstrap resolves /dnsaddr/bootstrap.bitllm.org. Each dnsaddr= TXT record at that name is one seed multiaddr, so seeds can be added or retired without a release. The production list currently names seed1.bitllm.org over TCP and QUIC. The node also carries the old boot.bitllm.org tunnel as a literal fallback for one more release. A --bootstrap value that names a peer directly is a join code; it works even when DNS does not.

Two details matter at this step:

  • Self-filter. A node removes its own peer id from the resolved addresses before dialing. A seed that is also a normal participant would otherwise connect to itself, reserve a relay slot on itself, and count a duplicate connection.
  • Failure is survivable. If the name does not resolve, the node tries the fallback; if that fails too, it starts alone, prints its addresses, and keeps redialing every 15 seconds. A join code supplied later is enough to attach it to the network.

The node asks DNS only for seeds. It does not resolve peers by name, and it does not use DNS to decide who serves a model.

Discovery

Two mechanisms run in parallel, because they answer different questions.

Gossip: who is online now

Every node subscribes to a libp2p pubsub topic, and a serving node publishes an announce every 10 seconds. The announce is small and unsigned beyond transport identity:

{
  "v": "v0.4.6",
  "models": ["Qwen/Qwen3.8-Flash-Next"],
  "free": 1, "max": 2, "q": 0,
  "relay": true,
  "loc": "u33",
  "weights": {"Qwen/Qwen3.8-Flash-Next": "sha256-..."}
}

An announce is trusted only while it is fresh: a peer last seen within 3 × announce interval + 5 s (about 35 seconds) is a routing candidate. That gives fast failure detection without a heartbeat server. A server that stops answering goes quiet on its next failed upstream check, and clients stop choosing it within three periods.

DHT: who serves this model, ever

Gossip may not have reached a node that just started, so every serving node also publishes a provider record under a key derived from the model name:

key = sha256("bitllm/model/" + model)

The key keeps the exact model string, including case and slashes, so Qwen/Qwen3.8-Flash-Next is a different key from qwen/Qwen3.8-Flash-Next. A client with no candidates for a model asks the DHT for its providers and connects to them; this is the cold-start path. Provider records are refreshed every two minutes and expire after a day, so an offline node eventually leaves the index.

The DHT stores routing and provider records, not model files and not inference results. It is a phone book, not a switchboard.

Connectivity

Most nodes are behind NAT or CGNAT. A node that can accept inbound connections listens on TCP and QUIC (UDP) 4001. A node that cannot still participates:

  1. It reserves a slot on a relay: the seeds first, then public relays discovered through gossip. The reservation is a libp2p circuit address.
  2. Peers dial the circuit address. The relay forwards the first bytes and never sees plaintext, because the stream is end-to-end encrypted.
  3. Both sides attempt hole punching. If the routers allow it, the connection upgrades to direct and the relay leaves the path. If not, the circuit stays for the life of the stream.

Relay candidates are the seeds plus every recently seen peer that announced relay=true, shuffled so a new public relay gets traffic without a coordinated rollout. A node limits how many relays it reserves on, and it never treats a relay as a model server unless that relay also serves the model.

Transport encryption is Noise/TLS/QUIC depending on the transport. The serving machine still reads the plaintext prompt; encryption protects the path, not the endpoint.

Request path

The gateway listens only on localhost. A request goes through these steps:

  1. Parse and bound. The body is read up to a fixed limit, the model is read, and image-heavy requests are defused for older peers. Malformed JSON is a 400.
  2. Own model first. If this node shares the requested model and its upstream is up, the request is answered locally. It never leaves the machine, costs nothing, and is not metered as network work. If the local server is down, the gateway falls through to peers that serve the same model.
  3. Candidates. Peers are filtered by fresh announce, by model, by weight hash when the model manifest records one, and by audit status. They are ranked by free slots, queue depth and measured latency. A peer never dialed has no latency and ranks behind a peer that just answered.
  4. Try up to three. For each candidate the gateway opens an inference stream with a bounded wait. A server with no free slot keeps the request in its own queue; the client waits up to its own deadline. A server that refuses the caller outright (403, an allow list) is skipped for the rest of the request.
  5. Stream. The serving node forwards the upstream response. Tokens are written to the local client as they arrive; a disconnect on either side tears down the stream. The response carries X-Bitllm-Peer, the peer id that answered.
  6. Retry or fail. If every attempt was busy, the gateway backs off, refreshes the candidate list, and tries again until its deadline. If nobody serves the name, it returns 503 no peer serves model X. If every server refused, it returns the status they gave, with all peers refused. If everyone failed, it returns 502 all peers failed.

Both OpenAI (/v1/chat/completions, /v1/completions) and Anthropic (/v1/messages) shapes are accepted. The gateway does not translate between them; it forwards the shape the client sent, so the serving upstream must support it. vLLM supports both.

Queueing is per server, not global. A server orders waiting requests by access class first, then by arrival; a request's class improves one step every 20 seconds of waiting, never past the best class, and after that the longest wait goes first among equals. A full queue refuses immediately rather than accepting a place that does not exist.

Serving

A serving node points at an OpenAI-compatible base URL:

bitllm --upstream http://localhost:8000/v1 --concurrency 2

At startup it calls GET /models on that upstream. Unless --model was passed, every id the server reports becomes a public model name, unchanged. While the node runs, it re-reads the list every 30 seconds when the upstream is idle, so a model added to vLLM later appears without restarting BitLLM. A model removed from the upstream disappears from announces and the DHT on the next refresh. Passing --model pins the mapping: it is for renaming a local id, or for sharing a subset, and it stops the refresh.

Other serving behavior:

  • Concurrency. --concurrency is how many requests the upstream can take in parallel. Extra requests wait in the node's queue; the announce reports free slots and depth so clients can choose.
  • Images. If the upstream caps images per prompt (vLLM's --limit-mm-per-prompt), the node learns the cap from the first refusal and keeps only the newest N images, replacing older ones with a short note. Long agent sessions therefore do not fail on every turn.
  • Token cap. --max-tokens bounds new tokens per peer request (default 32768). A peer gets one choice per request; n is dropped.
  • Quotas. --free-daily sets a per-member daily quota; the default is unlimited. A contributor is never limited by quota.
  • Allow lists. --allow PEER_ID serves only the listed peers and refuses everyone else. The error names the caller's peer id, so the owner can add it.
  • Weights. --weights NAME=HASH states what the server loads, from bitllm hash-model DIR. It is a claim, not a proof. When the model manifest records a canonical hash, clients skip peers that announce a different one.

A node that shares a model answers that model itself first. Its own traffic never consumes a network slot, and it does not earn credits from itself.

Model names

A model name is the string clients send. Two machines that announce the same string are interchangeable for it: the gateway picks one, and if it stops answering it tries another. The name must therefore identify the weights, not the machine.

  1. A public model uses its exact Hugging Face repo id. Qwen/Qwen3.8-Flash-Next, with the slash and the case as published. Independent hosts that serve the same repository match without a central registry, and one can replace another when it goes down.
  2. A fine-tune or quant uses the repo id of the actual weights when it has one; otherwise the base id plus a suffix that says what changed. One name means one set of weights. Example: Qwen/Qwen3.8-Flash-Next-fp4-alesha.
  3. A private or brand-new model can use any stable name. Nothing is registered first: the node announces it, GET /v1/models lists it, and the dashboard lets a user pick it. --model local=public exists only for the case where the server's local id is not the name clients should use.

The naming pattern is <model>[-<quant>][-<source>], joined with hyphens; the model part keeps the Hub id's case and slashes. Quant is the weight format when it is not the maker's release (fp4, nvfp4, int4, q4_k_m); source is who changed the weights (a fine-tune name, or the group that made the quant). How a server runs the model (vLLM or SGLang, context length, fixed sampling) does not change the name.

No registry is required. The optional table in the README lists reference names the beta has used; it is a convenience, not a gate.

Receipts and credits

Serving earns credits, and credits are countable without a ledger server:

  1. The client signs what it received: model, prompt and completion token counts, and a SHA-256 of the exact response bytes. It signs with a pseudonym, one key per server rotated every 30 days, so the receipt shows which server did the work but not who asked. That server can link one client's jobs to each other.
  2. The serving node checks the claim against what it sent and countersigns. A receipt that does not match the token formula is rejected.
  3. The receipt is gossiped. Any node can verify both signatures, recompute the credit (prompt tokens / 4 + completion tokens), and aggregate per server.

Credits are a public count, not a token or a promise. A new node catches up from its bootstrap peers; a node accepts at most 120 receipts a minute per server and 600 overall from gossip, which bounds flooding. Receipts live in ~/.bitllm/receipts.jsonl, and GET /credits returns the current table.

What counts toward future value is not decided yet. Self-dealing through fake clients, or serving a model other than the one named, is expected to be excluded when the rule is published.

Access

The beta is invite-only in the BitTorrent sense: no account is needed to try the network, and membership decides who gets a free slot first, not who can connect.

  • An invite is a signature from an Ethereum account. Nodes gossip invites; there is no membership server. Revoking an account removes everyone it invited.
  • A member is served on any free slot. An uninvited node is served only when a server is idle, unless its owner starts with --open.
  • Sharing makes a node a contributor: never limited by quota, and 10 invites instead of 3 once its nodes have served.
  • A server owner can still restrict serving to an allow list (--allow) or set a daily quota. Those are per-server decisions, not network policy.

The membership roots are Ethereum addresses in the binary's defaults. A node with no roots treats every node as a member, which is useful for a private test network.

Audits

A node can claim a model it does not serve. Auditing is an opt-in spot check, not a proof:

  • With --audit, about one request in 50 to a peer is followed by a canary request. Another node, the auditor, scores the answer token by token.
  • The default auditor is a node run by the maintainers. --auditor PEER_ID replaces it; --auditor none drops it.
  • A peer that keeps failing gets no requests for that model for 24 hours. GET /audits shows the results.
  • It finds a server running a different model, and a coarse quant on greedy requests. It does not find a server that recognizes canaries, a quant swap on sampled requests only, or a light fine-tune swap. An auditor can lie in either direction. A shuffled control catches only an auditor that passes everything.

Auditing is off by default because it costs a second request and a second node. Turning it on improves the experience for that node without changing the network's guarantees.

Privacy boundary

  • The serving peer reads the prompt in plain text. Transport is encrypted, but the GPU host is an endpoint. Do not send secrets.
  • A peer you connect to directly sees your IP address. A relayed peer sees the relay's address instead. The serving peer sees your node id either way.
  • A location is opt-in. --location LAT,LON is turned into a three-character geohash cell (about 156 km by 156 km) before it leaves the machine. The point itself is never announced. Without it, the node is counted as "no location".
  • IP geolocation is not used, on purpose: it would place people who never asked, and for relayed nodes it would often place the relay instead.
  • Receipts are pseudonymous. A client signs with one key per server, rotated every 30 days, so a receipt links a server to work but not to the person who asked. That server can link one client's jobs to each other.

Operations

Run a seed

bitllm --dht-server --port 4001 \
  --announce /ip4/203.0.113.10/tcp/4001 \
  --announce /ip4/203.0.113.10/udp/4001/quic-v1

A seed starts without joining the default seeds (it may be the only one), answers DHT queries, and relays. It needs no GPU. Open TCP and UDP 4001 in the firewall and the cloud security list; TCP alone works but loses QUIC and some hole punching. Announce the public address explicitly when the machine is behind a 1:1 NAT, or the node will advertise its private one. Publish the seed's multiaddr as a dnsaddr= TXT record at _dnsaddr.bootstrap.bitllm.org.

Run a public relay

bitllm --public --port 4001 \
  --upstream http://localhost:8000/v1 \
  --announce /ip4/203.0.113.11/tcp/4001 \
  --announce /ip4/203.0.113.11/udp/4001/quic-v1

--public is a public DHT server and relay that still joins the default seeds. It must also serve a model, because only a serving node announces. It needs no DNS record: NATed nodes discover it through its relay=true announce and add it to their relay candidates. This is how relay capacity grows without editing DNS.

Keep a node running

Use a systemd unit (Linux) or a LaunchAgent (macOS) with restart-on-failure. Keep the data directory: it holds the peer identity, receipts, claims and quota state. A node that loses its data directory comes back as a new peer.

Updates

A release build checks for a newer release 30 seconds after start and every 6 hours, verifies the binary against the release's SHA256SUMS, and restarts in place when the node is idle: same unit, same peer id. --auto-update=false disables it; bitllm update installs now. The previous binary is kept as bitllm.prev. Builds from source never update themselves.

Ports

4001 TCP and UDP is the p2p port. 7778 is the local gateway and listens on 127.0.0.1 only. The gateway refuses non-local Host headers, so a browser on the LAN cannot reach it by the machine's name.

The map

Every node can produce an aggregate of the network at GET /network: counts per model, per version, and per ~156 km geohash cell, plus how many nodes did not declare a location. It contains no peer ids and no addresses.

The map at bitllm.org is a snapshot of one node's /network, copied into Cloudflare KV about every ten minutes by a scheduled job and served as /network.json. The uploader never accepts inbound requests. The page fetches the snapshot once a minute; if the key is empty it shows an empty network rather than failing. Counts are for serving nodes only, so a client-only node does not appear.

Only operators who passed --location are placed. The rest are counted in the "no location" bucket. Nothing is inferred from IP addresses.
